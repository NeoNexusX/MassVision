# 聚类分析（UMAP）功能 — 前端对接指南

> 日期：2026-08-15
> 面向：前端开发
> 范围：聚类分析（UMAP）功能的接口调用、状态轮询、结果读取

## 一句话概述

对一个**已完成算法处理**的 run 执行 UMAP 分析，分析结果（降维坐标/分组数据）**直接写回该 run 原有的 zarr 内部**，不再产生独立的结果目录。前端只需：触发一次 → 轮询状态 → 用原来的 zarr 读取方式拿结果。

## 整体流程

```
POST /processes/{run_id}/clustering        触发聚类（立即返回，异步执行；幂等，可直接轮询）
        ↓
重复 POST 同一接口（或 GET /processes/mine）  轮询 clustering_status
        ↓ clustering_status == "completed"
GET /processes/{run_id}/zarr               拿 OSS STS 凭证（和原来完全一样）
        ↓
前端用 OSS SDK 直连读 zarr，新增的分析数据已在其中
```

## 1. 触发聚类

**`POST /processes/{run_id}/clustering`**（需登录态）

| 项 | 说明 |
|---|---|
| 入参 | 仅路径参数 `run_id`，**无请求体**（聚类参数由服务端固定，前端不传） |
| 前置条件 | 该 run 的算法处理必须已完成（`status == "completed"`）；仅记录所有者或管理员可触发 |
| 返回 | `ExperimentProcessRunPublic`（见下文字段说明） |

**幂等行为**：若 `clustering_status` 已是 `processing`、`completed` 或 `failed`，接口直接返回当前记录、**不会重复触发**（failed 也不自动重试）。

> ⚠️ **当前版本已知问题**：`failed` 状态的幂等短路在**下个版本**才上线。当前线上版本中，`failed` 状态下再次 POST **会重新触发任务**。因此当前版本前端请注意：轮询拿到 `failed` 后**必须立即停止**调用本接口，重试只能由用户显式点击触发。下版本上线后此限制解除，任何状态下轮询都无副作用。

**失败情况**：校验不通过（run 不存在 / 无权限 / 算法未完成）返回 4xx 业务错误码，按现有错误处理流程提示即可。

## 2. 状态轮询

聚类是异步任务，有两种轮询方式，**推荐方式二**：

### 方式一：`GET /processes/mine`

通过现有分页列表接口返回的每条 run 记录中的 **`clustering_status`** 字段判断进度：

| 值 | 含义 | 前端建议 |
|---|---|---|
| `null` | 未执行过聚类 | 显示"开始聚类"入口 |
| `processing` | 进行中 | 显示加载态，继续轮询（建议 3~5s 间隔） |
| `completed` | 完成 | 显示结果入口，可读取 zarr |
| `failed` | 失败 | 显示失败提示，错误详情在 `error_message` 字段；**不会自动重试** |

适合已在列表页、顺带刷新状态的场景。

### 方式二（推荐）：复用触发接口轮询

触发接口 `POST /processes/{run_id}/clustering` **是幂等的**（任何状态下重复调用都不会重复触发，见上文），因此可以直接用它轮询——前端只需维护这一个接口：

```
首次 POST → 返回 clustering_status=processing（任务已触发）
之后每 3~5s 再次 POST → 返回最新的 clustering_status
直到返回 completed / failed，停止轮询
```

> ⚠️ **当前版本**：拿到 `failed` 后必须停止轮询（再次 POST 会重复触发，见上文已知问题）。拿到 `completed` 后同样停止轮询。

| 对比 | 方式一（`/processes/mine`） | 方式二（复用 POST） |
|---|---|---|
| 前端工作量 | 需在列表数据里找对应 run | 单接口闭环，最简单 |
| 额外请求量 | 每次拉整页列表 | 每次只查一条 run，更轻量 |
| 适用场景 | 已在列表页、顺带刷新状态时 | 详情页/专注聚类进度的场景 |

注意：方式二在 `clustering_status = null`（未执行）时调用**会触发任务**——只想查看历史状态而不触发时，用方式一。

## 3. 读取结果

**读取方式和读算法结果 zarr 完全一样**，聚类结果已合并进同一个 zarr：

**`GET /processes/{run_id}/zarr`** 返回：

```json
{
  "folder_path": "OSS 上的 zarr 文件夹路径",
  "bucket": "...",
  "region": "...",
  "sts_token": { "..." : "OSS 临时凭证" },
  "expires_in": 3600
}
```

前端拿到后用 OSS SDK 直连读取 zarr（支持 Range / 分块随机读），**与现有算法结果展示共用同一条代码路径**，无需为聚类单独写读取逻辑。

### ⚠️ 两处既有变更，前端必须同步

1. **不要再传 `zarr_type` 参数**：旧版 `GET /processes/{run_id}/zarr?zarr_type=clustering` 已删除该参数，聚类结果统一从 `out_path` 对应的 zarr 里读。如果前端还有带 `zarr_type` 的旧调用，请移除。
2. **分析数据在 zarr 内的 group 名**：UMAP 结果写在 zarr 内部的 `anay` group（由分析库写入）。前端渲染聚类图时从该 group 读取降维坐标即可；若解析不到，联系后端确认实际写入的 group 名。

## 4. 其他说明

- **删除行为**：删除 run（`DELETE /processes/{run_id}`）会连同其 zarr 一起删，聚类结果随之清除，前端无额外处理。
- **无新增鉴权逻辑**：全部接口沿用现有登录态 + 记录归属校验。
- **重复聚类**：`completed` 状态下接口幂等返回，不会重跑；`failed` 状态当前版本**再次 POST 会重新触发**（下版本修复为幂等），重试交互请做成用户显式点击，不要自动重试。
